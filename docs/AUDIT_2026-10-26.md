## Findings

### P2 — Background Google deletion cleanup can clear a newly signed-in account

Location: `CheeseApp/CheeseApp/Core/Services/AuthService.swift:1600–1628`.

Deletion now returns to logged-out UI immediately and schedules provider cleanup
in an independent task. Once deletion returns, `isLoading` is false, so another
Google sign-in can proceed while the old revocation request is still in flight.
The subject check runs only before `disconnect()` suspends. In the resolved
GoogleSignIn SDK, a successful disconnect callback calls the singleton's
`signOut()` unconditionally; the app also calls that same method on failure.
Both paths can clear the new Google user's SDK state and keychain entries.
This does not establish that the new Supabase session is revoked, but it breaks
the intended isolation between old-account cleanup and new-account login.

Reproduction scenario: delete Google account A with a delayed revocation request,
sign in to Google account B, then allow A's request to complete (success or error).
Evidence is control-flow review against the actual resolved SDK source, not a
live provider reproduction. The added finalizer test checks task scheduling only.

Suggested fix: serialize Google SDK sign-in against outstanding disconnect work,
while keeping local deletion immediate, or use a revocation path bound to captured
old credentials that does not clear the singleton on completion. A catch-only
subject recheck is insufficient because the SDK's success callback also signs out.
Add a delayed-cleanup/new-login regression covering success and failure.

### P2 — CI does not execute existing tests for recently changed database contracts

Location: `scripts/verify-app-store-db.sh:82–92`; invoked by the database job in
`.github/workflows/app-quality.yml`.

The script replays all migrations but runs a fixed list of ten SQL suites. It
omits existing tests for university expansion/verification
(`20260912041913`), V2 cross-school eligibility (`20260910024900`), continuation
(`20260910061558`), ignore penalty (`20260910190417`), and Home session lifecycle
(`20260910215652`). Thus a green database job does not validate these contracts,
including the school and eligibility paths relevant to the current working tree.

Suggested fix: include these suites in CI with their required policy fixtures,
and add explicit coverage for the gate-disabled rollback. Do not blindly run
historical tests whose expectations have been intentionally superseded.
